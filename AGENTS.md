# Working on csvview

## Purpose and scope

csvview is a local CSV viewer: Python and DuckDB serve a bundled browser UI.
Preserve CSV loading, filters, sorting, search, SQL, inspection, and export when changing
packaging or documentation. Keep the application local by default. This public repository
must contain no office data, credentials, or developer-specific paths.

This is the single repository instruction file for coding contributors and agents.
Follow the user's requested scope. Inspect the working tree before editing; preserve
unrelated changes. Do not start or stop a server belonging to another person or process.

## Setup and commands

Use Python 3.9-compatible syntax and uv. From the repository root:

```sh
uv sync --locked --extra dev
uv run csvview
uv run ruff check .
uv run pytest -q
uv build
```

The install is editable. Restart the Python process for backend edits; reload the browser
for frontend edits. No npm, frontend build, database service, credentials, or paid services
are required. Tests create synthetic inputs and temporary localhost servers.

After a build, check the installed wheel using the README's isolated test command.
Do not claim a package works based only on tests against the editable source tree.

## Folder and module map

| Path | Responsibility |
| --- | --- |
| `src/csvview/cli.py`, `__main__.py` | Arguments, process startup, browser launch, shutdown |
| `src/csvview/engine.py` | DuckDB tables, queries, view caches, stats, exports |
| `src/csvview/filters.py`, `values.py` | Filter-to-SQL translation and JSON value conversion |
| `src/csvview/server.py` | HTTP routes, errors, temporary transfers, static asset delivery |
| `src/csvview/static/` | Vanilla JavaScript modules, HTML, CSS; included in wheel and source archive |
| `tests/` | Behavior and distribution verification using synthetic inputs |
| `docs/` | Architecture, versions, changes |
| `.github/` | CI checks, tagged releases, PR template |

`pyproject.toml` owns package metadata, dependency declarations, build rules, and lint/test
configuration. `src/csvview/__init__.py` owns the version, read dynamically by the build.
`uv.lock` is generated by `uv lock`; never hand-edit it. `dist/`, caches, and virtual
environments are generated and ignored. User data belongs outside version control.

## Interfaces and data rules

The supported user entry points are `csvview` and `python -m csvview`, plus the browser UI.
The browser API is documented in `docs/OVERVIEW.md`; update both ends and tests together.
Python internals are not a promised stable third-party library API.

Keep SQL filter values parameterized and identifiers quoted through the existing helpers.
Do not interpolate user input into SQL. The SQL editor deliberately executes user SQL;
do not describe it as read-only or sandboxed. Keep default HTTP binding at `127.0.0.1`.
Do not add analytics, remote assets, or uploads to an external service.

Preserve null/NaN rules, exact large integers, date conversion, table-name deduplication,
and source-file integrity. Never silently discard malformed rows. Export applies filters
and sorting but not display-only hidden columns. Browser local storage contains settings,
filters, drafts, and SQL history; document any persistence change.

## Editing and review standard

Keep each module focused; extend existing helpers before adding competing abstractions.
Annotate Python interfaces, keep imports ordered, and follow the existing JS module style.
Comments explain constraints rather than narrating obvious code. Avoid unrelated refactors,
speculative framework changes, generated-file edits, and new dependencies without a need.

Add regression tests for behavior fixes and meaningful tests for new mechanisms. Run the
full tests and Ruff before committing. For frontend changes, exercise the UI yourself with
synthetic data; inspect rendering and browser errors. Stop temporary processes you started.
Build and test the wheel whenever changing packaging, dependencies, or static asset paths.

Read `docs/OVERVIEW.md` before changing module boundaries. Describe structural changes and
their impact before implementation; use the user's existing authorization for routine work.
Update README commands when behavior changes. Record shipped changes in `docs/CHANGES.md`.

## Git and pull requests

Inspect `git status --short` and `git diff` first. Work on the requested branch, or use a
focused feature branch for a contribution. Keep commits limited to one purpose and explain
the change and its verification. Never include private data or generated package files.

Follow the README's Pull requests section. Target `main`, fill in the template, include
actual verification results, and wait for CI and review. Push or merge only when the user
has authorized it. Publishing this repository or a release is not permission for unrelated
future pushes, branch deletion, or force pushes.

`main` is the immediate user update channel. Users reinstall its GitHub archive to receive
new code even without a version bump. This makes review before merge especially important.
Tags `v<VERSION>` trigger the release workflow; never move a published tag. Follow the
README release procedure, update the version once, regenerate the lock, and verify artifacts.

## Handover

Report what works, commands actually run, failures or untested platforms, current branch,
and remaining work. Never claim CI passed before reading its result. Keep unfinished work
and unrelated user changes identifiable; do not hide failures in a completion summary.
